# The doughknee.com site

Three pages, built by one script from the files in this directory:

| Page | Source |
|---|---|
| `https://doughknee.com/peggy/` | `build.py` |
| `https://doughknee.com/peggy/privacy/` | `../docs/PRIVACY.md`, rendered by `build.py` |
| `https://doughknee.com/` | `build.py` |

Everything under `peggy/`, plus `index.html`, `robots.txt` and `sitemap.xml`, is
**generated**. Do not hand-edit them; they are overwritten on every build. The
things you actually edit are `build.py`, `screenshots.json`, the PNGs in
`screenshots/`, and `../docs/PRIVACY.md`.

Build it:

```bash
python site/build.py
```

Look at it:

```bash
cd site && python -m http.server 8899 --bind 127.0.0.1
```

then open <http://127.0.0.1:8899/peggy/>.

The build needs nothing but the standard library, except Pillow for the image
step. Without Pillow it reuses the committed WebP files instead of re-encoding,
so the page always builds — but a new PNG would then be silently ignored, which
is why CI installs Pillow before building.

---

## 1. Replacing one screenshot

Drop the new PNG over the old one, keeping the file name, and rebuild:

```bash
cp new-sort.png site/screenshots/sort.png
python site/build.py
```

Commit both the PNG and the regenerated `site/peggy/shots/sort.webp`. That is
the whole procedure — no manifest edit, no HTML edit.

The new shot should be the same shape as the one it replaces. It does not have
to be 1080×2400: the build reads each PNG's real dimensions and writes them onto
the `<img>`, so the page reserves the right space for whatever you give it. But
the `.phone` frame around it is a fixed width, so a screenshot from a
differently-shaped device will look wrong next to the others even though it will
not distort.

## 2. Retaking all of them from a device

Two scripts, in this order:

```bash
python site/demo_data.py     # writes the demo content into the app's database
python site/screenshots.py   # drives the app and writes site/screenshots/*.png
```

Both take the same three flags:

| Flag | Default |
|---|---|
| `--serial` | `emulator-5554` |
| `--package` | `com.peggy.app.dev` |
| `--adb` | `~/AppData/Local/Android/Sdk/platform-tools/adb.exe` |

`screenshots.py` also takes `--only`, to retake a subset instead of all eight:

```bash
python site/screenshots.py --only sort ideas
```

Then `python site/build.py` to re-encode and rebuild.

> **`demo_data.py` is destructive.** It deletes every row in the target app's
> database before inserting the demo content. Point it at the emulator, never at
> a phone you care about. It has never been run against a real device and should
> not be.

Dates in the demo content are relative to the day you run it, so the screenshots
never show a stale week — that is the reason to re-seed rather than keep an old
database around.

## 3. Adding a new screenshot

Three steps, all required:

1. Take the PNG and put it in `site/screenshots/`.
2. Add an entry to the `shots` list in `site/screenshots.json`:
   ```json
   { "id": "search", "file": "search.png",
     "alt": "What the screen shows, described for someone who cannot see it.",
     "caption": "The line printed under the phone on the page." }
   ```
3. Reference the id from a section in `build.py` — `phone(shots["search"])` for a
   bare frame, or `figure(shots["search"])` to get the caption with it.

A shot listed in the manifest but referenced nowhere is encoded and committed but
never shown. That is not an error and the build will not complain; `calendar` is
in exactly that state today.

The build *does* fail if the manifest names a file that is not in
`site/screenshots/`, so a typo cannot ship a broken image.

## 4. Changing the demo content

Edit `build()` in `site/demo_data.py`. Write dates relative to today rather than
as fixed dates, the way the existing entries do, so re-running it later still
produces a plausible week. Then re-run the two scripts from section 2.

`site/demo_data.sql` is generated by that script on every run and is gitignored.
Do not commit it or edit it by hand.

## 5. What the device needs

- An emulator with root (`adb root`), for `demo_data.py` to write into the app's
  database. A normal phone will not allow it.
- The dev build installed on it (`com.peggy.app.dev`).
- `adb` reachable. It is not on the PATH in Git Bash here, so both scripts
  default to the SDK location above; use `--adb` if yours lives elsewhere.

`screenshots.py` puts the system UI into demo mode for a clean status bar — fixed
clock, full signal, no notification icons — and always turns it back off in a
`finally`, so an interrupted run does not leave the device with a fake clock.

## 6. Swapping the CTA at launch

Peggy is in closed testing, so every call to action points at the testing opt-in
page rather than the store listing, which would 404 today. Two constants at the
top of `build.py` control it:

```python
PRIMARY_URL = TEST_URL          # -> STORE_URL when it reaches production
PRIMARY_LABEL = "Join the test on Google Play"   # -> "Get it on Google Play"
```

Change those two, rebuild, commit. `STORE_URL` is already defined just above.

## 7. Deploying

`.github/workflows/pages.yml` builds and publishes on any push to `main` that
touches `site/**` or `docs/PRIVACY.md`. There is nothing to run by hand.

## Reviewing a change

`review.py` screenshots the served page with Playwright, writing into the
gitignored `site/review/`:

```bash
python site/review.py --full          # 390, 820 and 1440, light and dark
python site/review.py --nojs          # JavaScript off, to prove nothing is hidden
python site/review.py --probe         # the numbers a screenshot cannot show you
python site/review.py --segments      # the whole page, one readable screenful at a time
```

`--segments` is how you look at the page. A full-page PNG of this page is over
13,000 px tall and is unreadable once it is scaled down to view, which is how a
missing caption survived five sessions of "checked the full-page capture". One
viewport-sized PNG per screenful is readable at 1:1.

`--probe` is the one to run before committing a CSS change. It measures seven
things and exits non-zero if any of them fail:

- **overflow** — `scrollWidth` against the viewport at 390, 820 and 1440 in both
  themes. Anything larger is a sideways scrollbar.
- **sweep** — every width from 360 to 1680 in 20 px steps, not only the three
  the rubric names. It fails on overflow at any of them, and on the `.pair`
  phone duos flipping between side by side and stacked more than once. One
  transition is the design; a second and third mean some band in the middle has
  a column too narrow for its phones. That is exactly what 900–1060 was, and
  checking only 390, 820 and 1440 never saw it.
- **motion** — fast-scrolls the page and samples the computed opacity of every
  `.reveal` sitting in the middle 20–80% of the viewport, which is where a
  reader is looking. Any value below 1 there means the animation is delaying
  reading. This is why the reveal moves but does not fade: a fade always loses
  the race against a fast scroll, and half-transparent text is unreadable text.
- **anchors** — follows every in-page link (`#main` from the skip link, `#how`
  from the hero's "See how it works") at all three widths and fails if the
  target's own eyebrow or heading lands under the 65 px sticky header. There is
  no `scroll-margin-top` per target; `html{scroll-padding-top:80px}` covers
  every anchor, including ones added later.
- **text size** — reads every text element's computed size, sets the root to
  24 px (Chrome's “Very large”), and reads them again. Anything that did not
  move ignores the reader's own font-size setting. It also re-checks
  `scrollWidth` at that size, because bigger text is where overflow would
  appear. Every size on the page is `rem` or `clamp()`; a single `px` in the
  `font:` shorthand on `body` froze 36 of the 90 lines on `/peggy/` — both
  hero buttons, the skip link and the whole FAQ — under headings that grew
  1.5×. No capture taken at default settings can show this.
- **hidden** — loads with JavaScript off and with reduced motion asked for, and
  fails if anything is transparent or displaced in either. Hiding is opt-in
  (`html.js-reveal`), so both of those loads must show everything.
- **themes** — measures every opaque painted surface against whatever is
  actually behind it, in both colour schemes, and joins the two runs element
  by element. It fails on any surface that is solid in one theme (3:1 or
  better) and invisible in the other (under 1.05:1) — the signature of a
  colour that was chosen once and never re-chosen. `.phone` was a hardcoded
  `#0d0d12` on an otherwise fully tokenised page: 18.75:1 against the light
  `--bg` and 1.01:1 against the dark one, the same colour to within one RGB
  unit. In dark mode the bezel simply was not there and all eight
  screenshots floated. Neither theme looks wrong on its own, which is why
  this compares them rather than scoring each.

Two things it has already caught, worth knowing before you trust an image from
it:

- **Lazy images composite blank.** Anything below the fold with `loading="lazy"`
  screenshots as an empty white frame unless the page is scrolled through first.
  `scroll_through()` does that with the mouse wheel, which works with JavaScript
  disabled where `page.evaluate` does not.
- **Three good widths are not a responsive check.** 390, 820 and 1440 all
  passed while every width from 900 to 1060 was visibly broken. Breakpoints put
  the bugs *between* the widths you test, which is why `sweep` walks the range
  instead of sampling it.
- **A theme is not checked by looking at one theme.** The light page was
  right and the dark page was wrong, and each looked deliberate in
  isolation — the defect only exists in the comparison. Any colour written
  outside the two `:root` token blocks is a colour that was chosen against
  exactly one background.
- **A sticky header eats anchor landings, and only at some widths.** At 820 and
  1440 both in-page links landed fine; at 390 the skip link put 17 px of the
  `<h1>` under the bar and "See how it works" put 9 px of the Capture eyebrow
  under it. The two widths that pass are not evidence about the third.
- **Colour cannot be judged from a scaled capture.** A full-page PNG of this page
  is over 13,000 px tall, and downscaling it shifted the dark-theme link colour
  enough to look like a contrast bug that was not there. Crop at
  `device_scale_factor=2` before believing anything about colour.
